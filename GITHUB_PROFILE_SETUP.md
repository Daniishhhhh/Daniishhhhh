# GitHub profile setup checklist

This repository can improve the profile README, but account settings and contribution attribution must be changed in GitHub by the account owner. Complete the items below from the profile settings page.

## Profile essentials

1. Set the bio to a compact, evidence-based line such as: `CS undergraduate building AI/RAG, backend, and security-focused applications.`
2. Add Bengaluru, India (only if you want your location public), the portfolio URL `https://danish-portfolio-khaki.vercel.app/`, and the current LinkedIn URL.
3. Keep the display name consistent as **Danish Sidiq Rather**. The current public display name is styled differently from the README name.
4. Enable **Activity overview** in profile settings if it is not already visible. Do not rely on a README widget to replace it.

## Contribution accuracy

1. In **Settings → Emails**, add and verify every email address used in Git commits. Use a verified address for future commits, or GitHub’s `noreply` address.
2. In **Settings → Emails**, enable the option that keeps the email address private only if you also use the GitHub-provided noreply address in commits.
3. Check that substantive commits land on the repository’s default branch (usually `main`) or `gh-pages`; commits only on other branches do not normally count until merged.
4. In the profile contribution settings, choose whether to show private contributions. This only displays a private-count indicator; it does not reveal private repositories or turn them into public activity.
5. Review work made in forks, organizations, or with another GitHub account. GitHub’s contribution rules differ for fork commits and organization repositories; do not rewrite history merely to alter the graph.

The native graph is authoritative. Third-party cards can lag, cache, or use different inclusion rules, so this README deliberately does not publish hard-coded contribution totals.

## Repository hygiene

For every pinned project, add a one-sentence description, 3–6 accurate topics, a setup section, environment-variable examples (never real keys), an architecture note, and a clear status. Add a live-demo link only after verifying it remains reachable. Archive abandoned experiments or label them clearly as learning prototypes.

Suggested topics where supported by the code: `rag`, `llm`, `fastapi`, `azure-openai`, `chromadb`, `ai-agents`, `workflow-automation`, `cybersecurity`, `machine-learning`, `spring-security`, `jwt`, and `rbac`. Use only those that apply to the particular repository.

## Interactive developer directory

This repository includes a dependency-free terminal application in `terminal/`. The README preview is static by design; its **Launch the interactive developer directory** link opens the real application after GitHub Pages is enabled.

1. Go to **Settings → Pages** for this repository.
2. Under **Build and deployment**, choose **GitHub Actions** as the source.
3. Push the workflow and run **Deploy developer directory** once from the Actions tab if it has not already run.
4. The expected public URL is `https://daniishhhhh.github.io/Daniishhhhh/`.

The deployment workflow publishes only `terminal/` and uses `contents: read`, `pages: write`, and `id-token: write`, which are the GitHub Pages deployment permissions it needs. No third-party runtime, analytics, or secret is required.
